- [x] **Accessible appearance: dark & high-contrast themes (2026-11-21):** Introduced a three-mode appearance system on `<html data-theme="...">` — warm light (default), warm near-black dark, and a WCAG-AAA black/white/amber high-contrast palette — all defined as token overrides in `tokens.css` (no framework, no SaaS gradients). A craft-styled header button cycles light → dark → contrast, persists the choice in `localStorage ("oc-theme")`, and the bootstrap script honors OS `prefers-contrast: more` / `prefers-color-scheme: dark` before first paint (no flash). Localized `a11y.skipLink` + `theme.*` strings added to all three i18n dictionaries.
- [x] **EU (GDPR + ePrivacy) compliance pass (2026-11-21):** Audited the client-side surface against the ePrivacy Directive (Hungarian 2011. évi CXII. tv. 13/A. §) and GDPR Art. 13, then closed both gaps found: (1) **Cloudflare Turnstile is now lazy-loaded** — the script is fetched on demand only after the visitor clicks an unlock button or starts filling the contact form (no third-party request on plain page load), with graceful demo fallback; the contact form now also renders a Turnstile widget (first `focusin`) and sends `turnstileToken` to the Worker, which the Worker already verifies. (2) **`PrivacyNotice.astro`** renders a localized, accessible "Data protection information" dialog (footer + contact form links) documenting controller identity, the full browser storage inventory (all keys are functional/strictly-necessary and written only after explicit visitor actions — the site sets zero cookies and no tracking), the form data flow with processors (Cloudflare, Resend), and GDPR rights. Full compliance analysis + institution checklist added as `docs/SECURITY_AND_PRIVACY.md` §6.
- [x] **Mandatory human verification for every relayed email (2026-11-21):** `POST /api/contact/send` in the Worker now **requires** a valid Turnstile token — requests without one (curl, bots) are rejected with `403` *before* the Resend API is called (previously the token was optional, leaving a direct-spam hole). Client side, the contact form refuses to send until the Turnstile challenge returns a token (bounded 15 s wait, progress + localized failure feedback via `contactForm.verifyError` in hu/en/de, widget reset after each send). Site deploy is automated via CI; the Worker change needs a one-command manual deploy (see `docs/SESSION_HANDOVER.md`).
- [x] **Contact form email relay operational (2026-11-22):** Diagnosed the full email chain: the live Worker had only `TURNSTILE_SECRET_KEY` + `VAULT_MASTER_KEY`, so every real form submission would have failed at the Resend call (the Resend/OAuth config was a documented deferral — see `docs/CLOUDFLARE_SETUP.md` scope note). Fixed by setting the `RESEND_API_KEY` and `CONTACT_RECIPIENT_EMAIL` (the institution's public address) Worker secrets via the Cloudflare REST API (secret list now shows all four). Verified the Resend side end-to-end from this session: the sending-only API key works (probe to the account-owner address returned `200`), the sending domain is **verified** (probe to a non-owner address would 403 otherwise), and a live test email from the institution's relay sender was accepted for delivery. Remaining inbound delivery was then completed end-to-end via the Cloudflare API (after adding `Zone Settings:Edit` to the session token): **Email Routing enabled** (status `ready`), MX records (`route1/2/3.mx.cloudflare.net`) plus a merged SPF TXT (`v=spf1 include:_spf.mx.cloudflare.net include:_resend.com ~all`) plus a DMARC record added via the DNS API, the destination address turned out to be already verified, and the rule (institution's public address → the owner's Gmail) was created (id `36388ff2…`). A probe email sent through the exact form path (Resend → Cloudflare routing → Gmail) was accepted for delivery.
- [x] **Browser Vault Manager + critical demo-key fix (2026-11-22):** Built the standalone, zero-dependency **Vault Manager** at `public/admin/vault.html` (+ `vault-manager.js`, `vault-crypto.js`, `vault-manager.css`): paste the master key, the browser decrypts the current vault in memory, staff/directors edit contact details, staff profiles, and gallery photos with drag-and-drop uploads (canvas EXIF/GPS strip → WebP), and save via a **single atomic Git commit** through the GitHub Git Data API (fine-grained PAT, `Contents: Read and write`) — or download the `.enc` files plus a placement README. Byte-compatibility with the CLI and `PrivacyVaultRuntime.astro` is proven by a Node-crypto ↔ WebCrypto roundtrip test. The tool detects the public demo key and refuses to bless it, localizes its UI (hu/en/de), auto-fills `owner/repo` from `config.yml`, stages orphaned-media deletions, and keeps keys/tokens in memory only. **While testing it, discovered a live-site integrity bug:** the "re-encrypt under the real key" step of commit `5ad5dc6` had silently fallen back to `generateDemoVault()` (the CLI's `.vault-raw/` fallback), so the deployed vault artifacts were encrypted with the *public demo key* while the Worker secret holds the real key — live visitors passed Turnstile but decryption failed. Fixed the root cause in `scripts/vault-cli.mjs` (encrypt now aborts without `.vault-raw/`; key loading no longer silently falls back to the demo key; `demo` output states which key it used) and re-encrypted all 9 vault artifacts under the real `.env` master key (roundtrip-verified via CLI decrypt). See `docs/VAULT_MANAGER.md`.
